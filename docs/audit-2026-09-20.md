JEV Gate audit, September 20, 2026

Audited commit: `f4e6414f0d005d340a0c8086cd13b1d8a282b663`.
Product objective supplied by Tim: a trusted review companion for work on GitHub and in agent harnesses.

JEV Gate has a useful foundation. Keep the shared review engine, typed results, batched questions, local diff support, and the GitHub adapter that reads configuration from the base commit without executing PR code. The main direction error was turning broad classifications into blocking verdicts before establishing complete inputs, actionable evidence, and reliable delivery. Those weaknesses matter more than inference cost or the number of rules.

The next release should answer four questions clearly: What did you review? What deserves attention? Where is the evidence? Is that finding still current?

The findings below distinguish reproduced behavior, code inspection, and product recommendations. Provider responses in the probes were synthetic. This audit does not establish Jev's accuracy on real changes.

**Additional reliability issues came from inspection and focused stubs.**

The GitHub collector stops after ten full pages, or 1,000 files. A stub reproduced that limit. It does not reconcile the result with `pr.changedFiles`, so the final result cannot explain collection omissions. The Action also fetches PR metadata and the mutable PR files endpoint separately, with no subsequent head check. A concurrent push can invalidate the association between collected content and the displayed SHA. The latter is a code-inspection risk, not a reproduced live GitHub race. See [GitHub collection](../src/github.ts#L89) and [Action collection](../src/action.ts#L119).

Sticky-comment discovery trusts the first matching marker regardless of author. A synthetic ordinary-user comment was accepted as the update target. Validate the bot identity and the stored result schema before using either the target or its previous numbers. This probe establishes target selection, not a live permission bypass. See [comment lookup](../src/github.ts#L123).

The watcher deduplicates only by raw diff hash. A new model, changed installed rules, or changed options can need a new assessment of identical code. Delivery is also stored in one pending slot without session identity. Test multiple sessions, disposal during a running review, and workspace changes before widening harness support. Current plugin tests exercise `core.ts`; they do not exercise `setup`, polling, or context delivery.

**The central product problem is the meaning of a finding.**

`danger-sensitive-area` asks whether a change affects sensitive logic and defaults to a blocking gate. A correct security repair or intended migration can satisfy that condition. The result establishes a reason to inspect the change; it does not establish an error. The current briefing says to fix a real finding even though changing sensitive logic can be the intended work. See [the rule](../src/rules.ts#L16) and [the briefing](../plugin/src/core.ts#L191).

Use that rule to request a focused review. Record who reviewed the sensitive change and what evidence they checked. Reserve defect language for a specific supported concern. Blocking behavior should be an explicit policy selected by the repository owner after the signal has demonstrated value.

Whole-diff probabilities leave too much work to the recipient. A reviewer seeing "breaking-change: 82%" must rediscover the relevant code and determine whether the compatibility change is intentional. The result schema has no finding location, evidence, suggested verification, or resolution. The sticky comment and agent briefing therefore display classifications without a complete review task.

Build the input around candidate files, functions, or hunks. Ask Jev narrow questions about those candidates. Attach the candidate's known location to the result. For cross-file compatibility questions, supply the relevant contract or caller context, or explicitly abstain. A generative reviewer can inspect an escalated candidate when an explanation requires reasoning. Jev itself does not generate explanations. This division follows [TypeSafe's workflow guidance](https://docs.typesafe.ai/concepts/how-to-build-with-system-one) and its [description of System One](https://docs.typesafe.ai/concepts/system-one).

Avoid claiming a line caused a result merely because it was near the classified code. Candidate locations, supporting evidence, and reviewer-confirmed defects should remain distinguishable.

Display binary probability and rubric severity as separate quantities. The current code divides a score by the maximum level and calls the result a probability. An expected level of 1 on a 0-to-2 scale becomes 50%, but that number is a normalized rating. It does not mean a 50% chance of a defect. Keep the original scale and, when useful, its distribution and confidence. See [evaluation](../src/rules.ts#L112) and [TypeSafe's Score contract](https://docs.typesafe.ai/primitives/score).

Cheap inference supports this workflow, but human attention should be the main optimization target. Measure how often a reviewer accepts a finding, how long verification takes, and how often the tool interrupts without adding value. Keep price and token counts in expandable details.

**The calibration work is useful exploratory evidence. It does not yet establish review accuracy.**

The repository has 18 hand-written samples. Expected directions live in Markdown and are not checked by the runner. The recorded measurements show that wording changes move answers and that some negatives remain difficult. That is useful evidence to preserve. There is no held-out corpus, complete set of labels across rules, measured false-positive burden on routine PRs, or tracked missed defects. The current command measures score distributions and run-to-run variation. See [sample documentation](../samples/README.md).

Repeated asking near a threshold can reduce some observed variation. It does not demonstrate correctness or independent corroboration. Measure the final averaged decision on held-out cases before relying on it. Pin a model version for evaluation; the default latest alias can change the behavior being measured.

Create a machine-readable label manifest, separate tuning samples from evaluation samples, and include realistic clean changes. Include intended security fixes, removals of obsolete tests, removed credentials, approved API migrations, quoted paths, large diffs, missing context, and misleading PR descriptions. Sample filenames currently become the synthetic PR title; use realistic or neutral titles and test sensitivity to that metadata.

Add adversarial descriptions and code comments to evaluation. TypeSafe explicitly documents that adversarial state can influence Jev 1.13, and that unrelated content in large states reduces accuracy. Typed output constrains the answer's shape; it does not establish the judgment's integrity. This audit did not attempt or demonstrate a live model bypass. See [Jev 1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

**A stronger shared architecture can stay small.**

Keep one library that accepts a normalized change snapshot and produces one versioned review result. GitHub, the CLI, and each agent integration should collect inputs and render that result. Avoid adding provider calls or policy decisions inside adapters.

The result needs the following information:

| Record | Required information |
| --- | --- |
| Snapshot | Base, head, working-tree content identity, relevant context, and repository scope. |
| Policy | Source, fingerprint, enabled rules, thresholds, and enforcement mode. |
| Coverage | Reviewed, intentionally excluded, unavailable, and clipped content, with reasons. |
| Assessment | Rule and question versions, provider, resolved model, raw observations, and assessment health. |
| Finding | Stable identity, category, candidate location, evidence, requested verification, and resolution state. |
| Delivery | Recipient/session, snapshot identity, pending or delivered state, and superseding result. |

Keep assessment health such as complete, partial, or unavailable separate from findings such as needs review or confirmed issue. A result can be incomplete and still contain a valid finding. An empty finding list does not prove complete coverage.

For GitHub, lead with a short summary of coverage and actionable findings. Link to relevant code and show which findings are new, resolved, or accepted with a reason. Keep numerical details available. Preserve base-commit policy loading and avoid executing untrusted PR code. Revalidate the PR head before publishing and reject obsolete results.

For agent harnesses, start with a stable CLI/JSON contract. Add thin adapters for the user's actual hosts. Trigger review at meaningful checkpoints such as a completed edit batch, completed tests, or pre-commit, with a debounce for repeated changes. Polling can remain a fallback. Inject a compact, current review task with evidence and verification steps. Record the agent's disposition so an intentional change does not trigger the same intervention after every unrelated edit. Feedback is evidence for later evaluation; it should not silently rewrite policy.

A local deterministic secret check and explicit exclusion policy should run before sending content to a provider. This reduces avoidable exposure and gives precise findings for recognizable credential patterns. Semantic review can add context without becoming the only secret detector. Make provider destination and excluded paths visible in setup.

The documented incremental-review roadmap needs care. Reviewing only the newest edits can miss interactions and preserve findings that a later change resolved. First establish snapshot identity and finding lifecycle. Then cache assessments whose relevant content, context, model, and policy are unchanged. Reserve periodic full reconciliation for changes that invalidate earlier context.

**Recommended delivery order and acceptance criteria.**

1. Establish result integrity. Fix configuration discovery, coverage accounting, Git parsing, empty-result JSON, error status, stale delivery, and restart recovery. Acceptance: equivalent snapshots under the same policy have equivalent requests across adapters; omitted code never silently counts as reviewed; no finding reaches an agent after its snapshot has been superseded.
2. Make one review workflow useful. Start with sensitive-change review routing and a small set of located test or compatibility concerns. Add evidence and a disposition for each finding. Acceptance: a reviewer can locate the concern, understand the requested check, and record a resolution without changing a threshold to silence the tool.
3. Establish evaluation. Add machine-readable labels, held-out real changes, complete run identity, and adversarial cases. Report precision, recall, abstention, unavailable reviews, and intervention burden per rule. Set adoption targets before the pilot; they cannot be inferred from the present samples.
4. Run a pilot across GitHub and one active agent host. Evaluate accepted findings, missed defects found by humans, repeated interruptions, and time spent verifying. Expand adapters and consider opt-in enforcement only after that evidence supports them.

Defer additional rule packs, per-rule required checks, dashboards, and an autonomous fix loop until these steps work. Publication and installation polish can follow the stable result contract. A useful positioning statement is: "JEV Gate points reviewers and coding agents to changes that deserve another look, with evidence tied to the current code."

**Verification and limits.**

`npm ci`, `npm run typecheck`, and all 56 tests passed on the laptop with Node 26.0.0 and npm 12.0.2. The existing two-day dependency-age setting remained enabled. Rebuilding left committed `dist/` unchanged. The build emitted its existing `import.meta`-in-CJS warnings. Node 20 CI execution was not independently rerun.

Additional probes exercised the bundled CLI and Action against localhost provider/GitHub stubs, the actual plugin setup with a controlled context hook and fake child CLI, Git behavior in scratch repositories, and the review/state functions. These are implementation checks. They do not measure live Jev accuracy, real GitHub permissions/races, or a complete interactive OpenCode session.

The root production dependency audit reported zero advisories. The full installed graph reported 11 moderate package entries stemming from an OpenTelemetry advisory through the OpenCode dependency chain. That chain is a development dependency here and a runtime dependency of the separately installed plugin. Exploitability was not established. Track upstream remediation without conflating the count with 11 independent defects in JEV Gate.

Small adoption defects also remain: the README's pre-push example invokes `ev-gate` instead of `jev-gate`, and the rules documentation suggests changing a threshold in the same PR can override its review even though CI intentionally reads base policy. Fix these with an installation smoke test and consistent override documentation. The `v1` tag does exist remotely; its absence is not a current blocker.
